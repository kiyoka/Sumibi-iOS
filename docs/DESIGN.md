# Sumibi-iOS 設計書

## 1. 目的

Sumibi-iOSは、ローマ字または英語の文章をLLMで自然な日本語へ変換するiOSカスタムキーボードである。Emacs版Sumibiのモードレスな入力方式をiPhoneとiPadで実現する。

## 2. 製品原則

- 日本語入力をモードレスに保つ。利用者は英字QWERTY配列で入力し、明示的に変換を実行する。
- 変換を元に戻せるようにする。Undoで原文へ戻せなければならない。
- 外部サービスへ送るデータを最小限にし、ネットワーク利用を明確に説明する。
- LLMへのリクエスト中もキーボードの応答性を保つ。
- キーボードUI、変換処理、プロバイダー連携、設定保存を分離する。

## 3. MVPの範囲

### MVPに含める機能

- 英字QWERTYキーボード配列
- ローマ字および英語の入力
- 専用の変換キー
- LLMによる日本語変換
- 代替候補を表示する候補バー
- 原文へ戻すUndo
- OpenAI互換プロバイダーの設定
- コンテナアプリでのAPIキーおよびモデル設定
- コンテナアプリでのユーザー辞書の編集と共有
- キーボードの有効化と「フルアクセスを許可」の案内
- フルアクセス未許可、ネットワーク障害、タイムアウト、認証情報不正の明確なエラー表示

### 初回リリースに含めない機能

- フリック入力配列
- アンビエント変換
- ローカルMozcによる仮確定
- 日本語から英語への翻訳
- クラウド同期
- 音声入力

## 4. システム構成

### コンテナアプリ

役割：

- 初期設定およびキーボード設定手順の案内
- プロバイダー、エンドポイント、モデル、APIキーの設定
- プライバシーに関する説明と同意
- 変換テスト画面
- 入力内容を記録しない診断機能

### キーボード拡張

役割：

- QWERTYキーと候補バーの表示
- 現在のキーボードセッションで挿入した文字列の追跡
- 変換対象の決定
- 変換リクエストの開始とキャンセル
- 原文から選択候補への置換
- Undoによる原文の復元
- フルアクセスおよびネットワークエラーの案内

### SumibiCore

次の機能を持つ共通Swiftパッケージまたはフレームワーク：

- 変換リクエストとレスポンスのモデル
- ローマ字入力の追跡
- 変換対象の選択
- プロンプトの構築
- OpenAI互換HTTPクライアント
- 候補の解析
- 再試行、タイムアウト、キャンセルの方針
- プロバイダーに依存しないエラー型

### 共有設定

コンテナアプリとキーボード拡張は、機密情報ではない設定をApp Groupの`UserDefaults`で共有する。APIキーは共有UserDefaultsや共有ファイルへ保存せず、App Groupをアクセスグループとして利用する共有Keychainへ保存する。

APIキー共有の規則：

- APIキーの入力、更新、削除はコンテナアプリだけで行う。
- キーボード拡張は変換時の読み取りだけを行う。
- Keychain項目のアクセスグループには`group.org.sumibi.Sumibi-iOS`を明示する。
- 保護属性には`kSecAttrAccessibleWhenUnlockedThisDeviceOnly`を使う。
- `kSecAttrSynchronizable`を無効にし、iCloud Keychainで同期しない。
- 端末間のバックアップ移行を行わない。新しい端末ではAPIキーの再入力を求める。
- 「フルアクセスを許可」が無効な場合、キーボード拡張はAPIキーを取得・使用しない。
- APIキーをログ、エラー文、診断情報へ出力しない。
- Face IDまたはTouch IDによる毎回の認証は、IMEの操作性を損なうため要求しない。

識別子案：

- アプリのバンドルID：`org.sumibi.Sumibi-iOS`
- キーボード拡張：`org.sumibi.Sumibi-iOS.Keyboard`
- App Group：`group.org.sumibi.Sumibi-iOS`

これらの識別子は、Apple Developerアカウントの設定が確定するまでの仮案とする。

## 5. 変換の流れ

1. 利用者がSumibiキーボードでローマ字または英語を入力する。
2. キーボード拡張は、現在の有効な入力セッションで自ら挿入した文字列だけを記録する。
3. 利用者が変換キーを押す。
4. キーボード拡張が原文と限定された周辺文脈を取得する。
5. SumibiCoreが設定済みプロバイダーへ変換リクエストを送る。
6. 進行状況を表示している間も原文は表示したままにする。
7. 成功した場合、追跡中の原文を削除して第1候補を挿入する。
8. 候補バーにUndoと`さらに変換候補を取得`ボタンを表示する。
9. Undoで元の原文を正確に復元する。

変換候補：

- 初回変換は文脈に最も自然な候補1件だけをAPIへ要求し、応答速度と品質を優先する
- 初回変換後に利用者が`さらに変換候補を取得`を押した場合だけ、2回目のAPIリクエストを実行する
- 追加取得では、現在の通常変換、QWERTY入力のタイプミス補正、全ひらがな、全カタカナ、漢字多め、送り仮名をひらいた表記、英訳の順で7候補を要求する
- 第2候補は隣接キーの押し間違い、文字の抜け・重複・順序違いを文脈から推測し、入力意図に沿った自然な文章へ補正する
- 追加取得中も初回の変換結果を入力欄へ残し、進行状況を表示して重複リクエストを防ぐ
- 追加候補の取得操作は1回だけとし、成功・一部取得・失敗のいずれでも再取得ボタンは表示しない
- 重複除外後に7件未満でも取得済み候補を表示する
- APIには候補配列を持つJSONだけを返すよう指定し、候補の順序を維持する
- 重複候補と空の候補は除外する

カーソル移動、外部からの編集、キーボード切り替え、または文書コンテキストの不一致によって安全に置換できなくなった場合、追跡中の入力を無効化する。

## 6. キーボードUI

初期配列：

- 候補バーの下、英字1段目の上に`1`から`0`を並べた数字段
- 数字段と英字1段目の間に、ライト／ダークモードで明確に識別できる横方向の区切り線を表示
- 標準的な英字QWERTYの文字列
- 英字2段目の右端（`p`の下、削除キーの上）に`-`を配置
- 英字3段目と最下段の間に`,`、`.`、`/`、`?`、`!`を並べた記号段
- 削除キーは英字3段目の文字キー2個分の幅を確保する
- Shift、削除、数字・記号、地球儀、空白、改行
- 文字、数字、記号、空白、削除キーは、0.85秒以上押し続けると約0.085秒間隔で入力を繰り返す
- 変換、改行、Shift、記号パネル切替は誤操作を避けるためキーリピートの対象外
- すべての通常キーは押した瞬間に軽い触覚フィードバックを返す
- 触覚フィードバックはアプリのキーボード設定でON／OFFでき、App Groupへ保存する。初期値はON
- キーボード拡張は`UIInputViewAudioFeedback`を有効にし、通常キーの押下時に`UIDevice.current.playInputClick()`でiOS標準のキークリック音を鳴らす
- キークリック音は触覚とは独立してアプリのキーボード設定でON／OFFでき、App Groupへ保存する。初期値はON
- 長押しリピート中は、実際に文字入力または削除を行う各タイミングでキークリック音を鳴らす
- クリック音の音量や消音はiOS本体の設定に従い、独自の音源は同梱しない
- キーボード本体の左上・右上は連続カーブで丸め、内側背景を外枠の角丸に沿ってクリップする
- 記号パネルの開閉中は通常キーと記号キー段をレイアウト内の固定位置に保ち、パネルの高さだけを`0`から展開高さまで変更する
- キーボードの下端と通常キーの位置を安定させたまま、記号パネルが上方向へ滑らかに伸縮するアニメーションとする
- 開閉時に記号パネルを`isHidden`で出し入れせず、高さ・間隔・透明度を同期してキー配列の再レイアウトによるガクつきを防ぐ
- 候補バーには記号パネル用の取っ手や透明な当たり判定を置かず、候補や`Undo`などの操作を妨げない
- 上端の角丸は縦画面16pt、横画面12ptとし、候補バーも連続カーブの12ptで調和させる
- iPhoneの横向きではキーボード、候補バー、段間隔、上下余白をコンパクト化し、キーの操作性を保ちながらホストアプリの表示領域を確保する
- 視覚的に区別できる変換キー
- キー配列上部の候補バー
- 候補バーのSumibiアイコン直後に、アイコンと`読込`ラベルを持つクリップボード読込ボタンを固定表示する
- クリップボードは利用者が読込ボタンを押したときだけ取得し、現在のカーソル位置へ原文のまま挿入する
- 読み込んだ文字列は自動変換せず、利用者が変換キーを押すまで編集可能な状態で保持する
- クリップボード由来の変換対象は複数行、日本語、記号、`/`を含めた貼り付け範囲全体とし、通常入力の`/`境界規則を適用しない
- クリップボードの内容はログや永続領域へ保存せず、変換後も変更しない
- ホーム画面用は全面オレンジ背景と縮小した中央図柄を持つ、不透明なSumibiアイコン
- 候補バー左端に、アプリアイコンとは分離した透明背景のSumibiアイコンを固定表示
- キーボード用アイコンはテンプレート画像として表示し、ライト／ダークモードの`.label`色へ追従

記号一覧パネル：

- 最下段の`記号`ボタンをタップすると開く
- 展開中は最下段のボタン名を`記号[閉]`へ変更し、同ボタンをタップすると閉じる。`記号[閉]`は文字を小さくし、通常の特殊キーより幅を広げて1行で表示する
- `@ # $ % & * ( ) _ + = [ ] { } \ | : ; " ' < >`を3段で表示する
- 記号を入力してもパネルを閉じず、通常の入力追跡処理へ追加する
- 展開時だけキーボードと記号パネルの高さを増やし、閉じたときは通常の高さへ戻す
- `needsInputModeSwitchKey`が偽の場合は、iOSがキーボード外側に表示する地球儀を使う
- `needsInputModeSwitchKey`が真の場合だけ、`記号`ボタンの長押しで次のキーボードへ切り替える

候補バーの状態：

- 待機中：短い案内を表示するか、候補バーを隠す
- 変換中：進行状況とキャンセルを表示する
- 成功：変換候補、代替候補、原文を表示する
- エラー：簡潔なメッセージと、必要に応じて再試行を表示する

Sumibiアイコンにはアプリと同じ画像資産を使用し、候補バーのスクロール領域外に固定する。候補、メッセージ、進捗表示、Undoが横方向へ増えてもアイコンは左上に残る。アイコンは識別用の装飾であり、タップ操作やVoiceOverの読み上げ対象にはしない。

## 7. ネットワークとプライバシー

変換ではネットワークサービスと共有設定を利用するため、キーボードには「フルアクセスを許可」が必要になる。設定アプリへ誘導する前に、コンテナアプリ内でその理由を説明する。

プライバシー規則：

- 利用者が変換キーを押した場合に限り、文字列を送信する。
- 利用者が送信先を確認して第三者AIへのデータ送信に明示的に同意した場合に限り、API通信を行う。同意は送信先ごとに保存し、送信先の変更時には改めて同意を求める。利用者はコンテナアプリからいつでも同意を取り消せる。
- App PrivacyとPrivacy Manifestでは、第三者AIへ送る変換対象・周辺文脈・ユーザー辞書を「その他のユーザーコンテンツ」、目的を「アプリの機能」、利用者への関連付けを「あり」、トラッキングを「なし」として申告する。
- 送信する周辺文脈は、有用性を保てる最小量にする。
- 登録済みユーザー辞書は、変換対象に登録語が含まれるかどうかにかかわらず、その全内容をすべての変換リクエストへプロンプトとして含める。送信量が際限なく増えないよう、辞書には上限（100件・2,000文字）を設ける。
- ユーザー辞書を毎回送信することを、コンテナアプリのプライバシー説明で明示する。
- キー入力や変換対象の原文をログへ永続化しない。
- ユーザー辞書の内容をログへ永続化しない。
- 無関係なクリップボード、連絡先、位置情報、識別情報を収集しない。
- Sumibiが運営するサーバーでは変換リクエストを保持しない。
- 診断情報からAPIキーと入力内容を除外する。

既知のプラットフォーム制限：

- パスワードなどの安全な入力欄では、iOSが他社製キーボードをシステムキーボードへ置き換える。
- 一部の電話番号入力欄ではシステムキーボードが使われる。
- ホストアプリは他社製キーボードの利用を禁止できる。
- ネットワーク通信と共有コンテナへの書き込みには「フルアクセスを許可」が必要になる。

## 8. エラー処理

- フルアクセス未許可：リクエストを実行せず、設定手順を案内する。
- 設定不足：利用者をコンテナアプリへ誘導する。
- 認証エラー：API認証情報が無効であることを知らせる。
- レート制限：原文を保持し、再試行を提示する。
- タイムアウトまたはオフライン：原文を保持し、再試行できるようにする。
- キャンセル：原文を変更せずに元の状態へ戻す。
- 安全に置換できない状態：ホスト側の文字列を変更せず、候補だけを表示する。

## 12. 変換対象と入力追跡

### MVPでの決定

MVPでは、現在のSumibiキーボードセッションが挿入し、引き続き管理している入力だけを変換する。ホストアプリの文書から任意の編集範囲を推測してはならない。

これは意図的にEmacs版より狭い仕様である。キーボード拡張は文書プロキシを通してカーソル周辺の限られた文字列を読み取れるが、ホスト文書そのものや安定した選択範囲を所有していない。置換対象を追跡中の入力に限定することで、カーソル移動やホスト側の編集後に無関係な文字列を削除する事故を防ぐ。

### 追跡する入力

`CompositionTracker`は次の情報を保持する：

- `source`：直近の確定境界以降にSumibiが挿入した正確な文字列
- `revision`：単調増加するローカル編集リビジョン
- `expectedSuffix`：カーソル位置の文脈を検証するための、長さを制限した末尾文字列
- `isReplaceable`：自動置換を引き続き安全に実行できるか

追跡処理は通常の表示可能文字を原文へ追加する。文書プロキシの文脈が一致している場合、削除キーは末尾の拡張書記素クラスタを1つ削除する。改行、キーボード切り替え、明示的なリセット、または変換成功後に追跡内容を消去する。

`sumibi yakiniku ga sukidesu .`のような句を一単位として変換できるよう、空白と句読点も入力対象に含める。改行を確定境界とする。リクエストが際限なく大きくなるのを防ぐため、MVPの変換対象は最大512文字とする。それより前の文字列は、読み取り専用の周辺文脈として利用できる。

### `/`による変換開始位置

追跡中の入力に`/`が含まれる場合、カーソルに最も近い最後の`/`を変換開始位置とする。APIへ送る`source`は`/`の直後からカーソルまでとし、`/`自身とそれより前の文字列は送信しない。`ConversionSnapshot`はAPIへ送る`source`とは別に、ホスト上で置換する`textToReplace`を保持する。後者には境界の`/`を含める。

変換または候補の確定に成功した場合は、`textToReplace`を候補で置換するため、境界の`/`も自動的に削除される。変換失敗またはキャンセルの場合はホスト側を変更せず、`/`を含む原文を保持する。Undoでは`/`を含む`textToReplace`を復元する。`/`が存在しない場合は、従来どおり追跡中の入力全体を変換および置換の対象とする。

例：`今日は/sumibi yakiniku ga sukidesu .`では、APIへ`sumibi yakiniku ga sukidesu .`だけを送り、成功後のホスト側は`今日は炭火焼肉が好きです。`となる。

### 安全性の検証

リクエスト開始前と置換直前の両方で、取得できた`documentContextBeforeInput`の末尾が`expectedSuffix`と一致することを確認する。置換直前の検証では、リクエスト開始時に取得したローカルの`revision`とも一致しなければならない。

どちらかの検証に失敗した場合：

- ホスト側の文字列を削除または置換しない。
- 返された候補は手動確認用として保持する。
- 入力内容が変更されたことを短いメッセージで知らせる。
- 結果をコピーまたは閉じられるようにする。
- 次のキー入力から新しい入力追跡を開始する。

この規則により、カーソル移動、ホストアプリからの編集、音声入力、テキスト置換、リクエスト中の追加入力を安全に処理できる。

### 置換

有効な結果を受け取った場合：

1. 追跡中の末尾文字列とリクエストのリビジョンを再検証する。
2. `textToReplace`に含まれる拡張書記素クラスタごとに`deleteBackward()`を1回呼び出す。
3. 選択された候補を挿入する。
4. 原文、置換結果、新しい期待末尾文字列を含む`UndoRecord`を保存する。
5. 変換中の入力追跡を消去する。

削除回数はUTF-16の長さではなく拡張書記素クラスタを基準にする。これにより、絵文字や結合文字によって削除回数が不正確になることを防ぐ。

### Undo

カーソルがSumibiの挿入した正確な置換結果の直後にある場合に限り、Undoを利用できる。同じ末尾文字列検証を行い、置換結果を拡張書記素クラスタ単位で削除して原文を再挿入する。無関係な挿入や削除、カーソル移動、キーボード切り替え、新しい変換のいずれかが発生した場合、`UndoRecord`を無効化する。

### MVPで明示的に対象外とする事項

- ホストアプリで選択した任意範囲の変換
- 文書プロキシの文脈から文書全体を再構築する処理
- 安全性の検証に失敗した後の文字列置換
- アンビエント変換

## 13. キーボード状態機械

UIとコントローラーは、1つの明示的な状態値を使用する。ネットワークのコールバックにはリクエストIDを持たせ、実行中のリクエストと一致しなくなった場合は無視する。

### 状態

- `idle`：追跡中の入力がない
- `composing`：追跡中の入力が有効で、変換を実行できる
- `converting`：1件のリクエストを実行中で、原文は未変更
- `candidates`：変換に成功し、代替候補を利用できる
- `staleResult`：変換には成功したが、原文を安全に置換できない
- `error`：原文を変更せずにリクエストが失敗した

### 状態遷移

```mermaid
stateDiagram-v2
    [*] --> idle

    idle --> composing: 表示可能文字を入力
    composing --> composing: 文字入力または削除
    composing --> converting: 変換

    converting --> composing: キャンセル
    converting --> composing: リクエスト中にキー入力
    converting --> candidates: 有効な応答
    converting --> staleResult: 編集不一致後に応答
    converting --> error: 変換失敗

    error --> converting: 再試行
    error --> composing: 入力を編集

    candidates --> candidates: 代替候補を選択
    candidates --> composing: 原文またはUndo
    candidates --> idle: 新しい入力範囲へ移動

    staleResult --> idle: 結果を閉じる
    staleResult --> composing: 新しい文字を入力

    composing --> idle: 改行・キーボード切り替え
    composing --> idle: 文脈の検証失敗
    converting --> idle: 文脈の検証失敗
    candidates --> staleResult: 文脈の検証失敗
```

| 現在の状態 | 事象 | 次の状態 | 処理 |
| --- | --- | --- | --- |
| `idle` | 表示可能文字の入力 | `composing` | 文字を挿入して追跡を開始する |
| `composing` | 表示可能文字の入力または削除 | `composing` | 挿入または削除を行い、リビジョンを増やす |
| `composing` | 変換 | `converting` | 検証してスナップショットを作り、リクエストを開始する |
| `converting` | キャンセル | `composing` | リクエストをキャンセルし、原文を保持する |
| `converting` | キー入力 | `composing` | リクエストをキャンセルまたは無効化し、応答性を保つ |
| `converting` | 有効な応答 | `candidates` | 第1候補へ置換し、Undo記録を作成する |
| `converting` | 編集不一致後の応答 | `staleResult` | ホスト側の文字列を変更しない |
| `converting` | 失敗 | `error` | 原文を保持して再試行を提示する |
| `error` | 再試行 | `converting` | 再検証して新しいリクエストを開始する |
| `candidates` | 代替候補を選択 | `candidates` | 現在のSumibi変換結果を安全に置換する |
| `candidates` | 原文またはUndo | `composing` | 正確な原文を復元する |
| すべて | 文脈の検証失敗 | `idle`または`staleResult` | 自動置換を無効化する |

### 並行処理の規則

- 自動置換を制御できるリクエストは同時に1件だけとする。
- 新しいリクエストを開始するときは、前のタスクをキャンセルしてリクエストIDを更新する。
- キャンセルは協調的に行い、遅れて届いた応答は無視する。
- Main Actor上で状態変更を直列化する。
- 進行状況を表示するためだけに原文を削除してはならない。
- 再試行では新しいリクエストIDを発行し、文書コンテキストを再検証する。

### 候補の挙動

モードレスなSumibiの操作感を保つため、有効な最初の応答を直ちに挿入する。その後、候補バーに代替候補と「原文」を表示する。別の候補を選択できるのは、現在挿入されている結果と期待末尾文字列が一致する場合に限る。一致しない場合は`staleResult`へ移行し、置換しない。

初期のAPI契約では、1回のリクエストにつき優先順位を付けた候補を最大3件返す。プロバイダーが候補を1件だけ返した場合でも、候補バーには「原文」を表示する。

## 14. OpenAI互換API

MVPの実API通信には、互換サービスで広く利用できるChat Completions形式を使用する。外部SDKには依存せず、`URLSession`で`POST /v1/chat/completions`を呼び出す。

設定されたURLが`/v1`で終わる場合は`/chat/completions`を追加し、完全な`/chat/completions` URLの場合はそのまま使う。それ以外のベースURLには`/v1/chat/completions`を追加する。

リクエストの規則：

- `model`には共有設定に保存されたモデル名を指定する。既定値は
  `gpt-5.6-terra`とし、既存設定が空の場合もこの値を補完する。
- APIエンドポイントの既定値は`https://api.openai.com`とし、クライアント側で
  `/v1/chat/completions`を補完する。既存設定が空の場合も既定値を補完する。
- `messages`には、変換規則を示す`system`メッセージと、周辺文脈および変換対象を示す`user`メッセージを含める。
- APIキーがある場合は`Authorization: Bearer`ヘッダーへ設定する。
- ローカルの互換サーバーを考慮し、空のAPIキーも許容する。
- 応答時間の上限は初期値15秒とする。
- ストリーミングは初期実装では使用しない。
- 応答の`choices[].message.content`からJSONの`candidates`配列を読み取り、空および重複した候補を除外する。

HTTPエラーは、認証エラー、レート制限、サーバーエラー、その他のHTTPエラーへ分類する。エラー応答の本文には入力内容やAPIキーが含まれる可能性があるため、ログへ保存しない。

## 15. ユーザー辞書

製品名、固有名詞、人名など、一般的な変換では期待どおりになりにくい語句を利用者自身が登録する。設定アプリで複数行のテキストとして編集し、キーボード拡張は読み取りだけを行う。

### 書式

1行につき1件を「よみ = 変換後」の形式で記述する。

```text
sumibi = Sumibi
kiyoka = 清香
openai = OpenAI
ro-maji = ローマ字
```

- 行の最初の`=`だけを区切りとして扱い、前後の空白を取り除く。変換後の側には`=`を含められる。
- よみに使えるのはASCIIの印字可能文字のうち、大文字`A`〜`Z`と空白を除いたものとする。ローマ字（小文字）、数字、記号を書ける。`ro-maji`のように長音や区切りの記号を含むよみを登録できる。
- よみに空白を含められない。区切りの前後の空白は取り除くため、`yamada tarou`のように語中へ空白を挟んだよみは登録できない。複合語は`yamada-tarou`のように記号でつなぐ。
- ひらがな、カタカナ、漢字、全角英数、全角記号はよみに使えない。よみはSumibiのローマ字入力と照合するためのものであり、キーボードから渡るのはASCIIだけなので、日本語を書いても一致しない。
- 大文字・小文字を正確に維持する対象は変換後の側だけである。`sumibi = Sumibi`は、入力`sumibi`を製品名`Sumibi`として出力する指定であり、左辺は入力の見出し、右辺は出力の表記という役割の分担になる。
- 空行は無視する。
- コメント行は設けない。

### 設定アプリのUI

コンテナアプリの`Form`へ「ユーザー辞書」の行を追加し、編集は`NavigationLink`で開く専用画面で行う。`Form`の中へ`TextEditor`を直接埋め込むと、フォーム側と編集領域とでスクロールが競合し、辞書が長くなるほど編集しづらくなるため、編集は独立した画面へ分ける。

一覧側：

- 「変換テスト」の直上へ「ユーザー辞書」の行を置き、登録件数を添えて表示する。未登録の場合は「未設定」と表示する
- 登録した内容を同じ画面の「変換テスト」でそのまま確認できる並びにする

編集画面：

- 画面いっぱいの`TextEditor`を1つ置き、辞書全体を複数行のテキストとして編集する
- ナビゲーションバーの右へ「保存」を置き、保存は明示操作とする
- 検証エラーは画面上部へ表示する。ソフトウェアキーボードが画面下部を覆うため、下部では隠れる
- 画面下部へ「N件・N/2,000文字」の形式でカウンタを常時表示し、上限を超えた場合は赤字にして保存を無効にする
- 辞書が空の場合は書式例をプレースホルダとして薄く重ねる。`TextEditor`にプレースホルダの標準機能がないため、重ね合わせで実現する
- 書式の説明を画面下部へ常時表示する
- 変更したまま前の画面へ戻ろうとした場合は確認を表示し、「破棄」と「編集を続ける」を選べるようにする。変更がない場合は確認しない

`TextEditor`の指定：

- 等幅フォントを使い、行ごとの`=`の位置を揃えて対応を読み取りやすくする
- `textInputAutocapitalization`を`.never`にする。iOSの自動大文字化が、よみの大文字エラーを誘発するため
- `autocorrectionDisabled`を有効にし、ローマ字の自動修正を防ぐ
- `keyboardType`は既定のままとする。変換後の側へ日本語を入力するため、ASCII専用のキーボードは指定できない

### 検証

保存時に全行を検証し、1件でも問題があれば保存せず、行番号・理由・該当行の内容を一覧で示す。本文は書き換えない。

行番号だけでなく該当行の内容も示すのは、iOS 17の`TextEditor`が特定の行の強調表示にも選択位置の操作にも対応しておらず、行番号だけでは利用者が該当行へたどり着けないためである。

| 条件 | 表示する理由 |
| --- | --- |
| `=`を含まない | 区切りの「=」がありません |
| よみが空 | よみが空です |
| よみに大文字を含む | よみに大文字は使えません |
| よみにASCII以外を含む | よみにはローマ字と記号だけを使えます |
| よみに空白を含む | よみに空白は使えません |
| 変換後が空 | 変換後が空です |
| よみが重複 | よみ「sumibi」がN行目と重複しています |
| 件数が上限を超える | 登録が100件を超えています（N件） |
| 文字数が上限を超える | 2,000文字を超えています（N文字） |

よみはASCIIの小文字・数字・記号だけで構成され、空白を含まないため、重複の判定は単純な一致比較で行う。

### 保存と送信

- 利用者が入力した原文テキストをそのままApp Groupの`UserDefaults`へ保存し、再編集時に復元する。解析は読み取り時に行う。
- 上限は100件・2,000文字とする。
- 登録内容は全件を毎回の変換リクエストへプロンプトとして含める。送信とログに関する規則は§7に従う。
